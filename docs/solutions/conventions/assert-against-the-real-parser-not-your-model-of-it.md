## Context

The reach feature needs a sudoers drop-in that lets Tinstar run exactly two
`tailscale serve` invocations as root, unattended, so that revoke-at-shutdown
and repair-at-boot both work without a human present to answer a password
prompt (`bin/tinstar/reachGrant.js:1-16`). The rule is generated by
`buildReachSudoersRule` (`bin/tinstar/reachGrant.js:46-51`), and its scoping —
that it permits the two invocations and nothing else, no `up`, no `down`, no
`--operator`, no wildcard — was asserted by a full test suite in
`tests/cli/reach-grant.test.ts:27-88`.

Every one of those assertions called `grantPermits(rule, commandLine)`
(`bin/tinstar/reachGrant.js:58-67`), a hand-written matcher shipped in the
same change: it slices the rule after `NOPASSWD:`, splits on unescaped
commas, unescapes each piece, and checks for an exact match. That function
encodes an author's understanding of how sudoers parses and matches a
command list. It is not sudoers. Nothing in the original suite ran the rule
through `visudo`, the actual consumer of this artifact.

A code review asked for that missing step. Running `visudo -cf` against the
generated rule failed immediately:

```
syntax error
will ALL=(root) NOPASSWD: /usr/bin/tailscale serve --bg --yes --https=443 http://127.0.0.1:5273, ...
                                                                          ^
```

Column 91 is the `:` in `http://127.0.0.1:5273`. In sudoers(5), `:` is a list
separator, and inside a command argument it must be escaped as `\:`. The rule
had never parsed. `installReachGrant` in `bin/tinstar/commands/service.js`
runs `visudo -cf` on the staged file before installing it
(`bin/tinstar/commands/service.js:306-317`) specifically because a malformed
drop-in can lock every user out of sudo — so this grant could not have
installed on any host, ever. Meanwhile the test suite reported the scoping as
fully proven, all green.

The fix (`escapeSudoersArgument`, `bin/tinstar/reachGrant.js:42-44`, applied
per-token in `buildReachSudoersRule` at `bin/tinstar/reachGrant.js:47-49`)
came with its own near-miss. The new "prove this isn't vacuous" test needed a
fixture that real `visudo` actually rejects. The first candidate,
`will ALL=(root) NOPASSWD`, parses successfully — `visudo` reads the trailing
`NOPASSWD` as a reference to an undefined `Cmnd_Alias`, warns, and exits 0.
The working fixture, used in
`tests/cli/reach-grant.test.ts:259-264`, is the unbalanced
`will ALL=(root`. The correct set of characters to escape (`,`, `:`, `=`,
`\`) was itself determined empirically — writing candidate rules to a temp
file and running `visudo -cf` against each — rather than read off the
sudoers(5) man page, because the model-vs-reality gap was exactly what had
just failed.

## Guidance

When the artifact your code produces is *consumed by an external parser,
runtime, or tool* — sudoers, cron, a shell, a config-file loader owned by
another program, a wire format some other service decodes — a test that
checks that artifact against a matcher you wrote yourself is not testing the
artifact. It is testing whether your matcher and your generator agree with
each other, which they always will, because one author wrote both halves the
same afternoon with the same mental model.

The tell: **you wrote both the artifact-generating code and the code that
checks the artifact.** If nothing in the test path shells out to, links
against, or otherwise invokes the real consumer, the suite cannot fail for
the reason that matters — that the real thing rejects what you built. Search
your own test file for the tell before trusting it: if every assertion in
the file resolves against a function defined in the same PR as the code
under test, and the actual downstream consumer (binary, library, service)
never appears, that's the shape.

The cost is not "a subtle edge case slipped through." It's stronger: the
feature was flatly non-functional — `visudo -cf` in
`bin/tinstar/commands/service.js:311` would refuse the rule on every install,
on every host, unconditionally — while all eight test cases in
`tests/cli/reach-grant.test.ts:27-88` reported the scoping as fully verified.
A green suite is normally the strongest local signal available; here it was
actively misleading, because it measured agreement with a reimplementation
instead of correctness against the real target.

The fix is cheap relative to the failure mode:

1. **Invoke the real tool.** `tests/cli/reach-grant.test.ts:224-244`
   (`visudoCheck`) writes the generated rule to a temp file and shells out to
   `visudo -cf` — the actual parser, not a model of it.
2. **Skip, don't fake, when the tool is absent — but don't let CI skip.**
   `visudoAvailable()` (`tests/cli/reach-grant.test.ts:199-222`) probes for
   `visudo` on PATH and the tests use `it.skip` when it's missing
   (`tests/cli/reach-grant.test.ts:247`) — a developer box without `visudo`
   gets a skipped test, not a silently-green fake one. That is right locally and
   wrong in CI, where a skip would silently delete the only coverage of a bug
   that already shipped once: `TINSTAR_REQUIRE_LIVE_VISUDO=1` turns absence into
   a failure instead, and ci.yml sets it. Honest absence is fine on a laptop; on
   the gate it has to be loud.
3. **Prove the check is not vacuous with a fixture you've watched it
   reject.** `tests/cli/reach-grant.test.ts:259-264` asserts a malformed rule
   is rejected — and the fixture had to be swapped once, because the first
   one turned out to parse. The lesson generalizes past this bug: a
   not-vacuous fixture is itself a claim about the external tool's behavior,
   and that claim needs the same empirical check as everything else here.
   Don't assume a string "looks broken" — watch the real tool reject it.

This is the same discipline as
`docs/solutions/conventions/verify-a-guard-by-breaking-it.md`, one level
removed. That doc's practice is: break the thing your guard protects and
watch your own test go red, to prove the guard isn't vacuously green for the
wrong reason. It works because you control both the guard and the thing it
guards — breaking your own code and re-running your own test is a valid,
closed-loop proof. Here the "guard" that matters — will this rule actually
parse? — belongs to someone else's parser. Breaking your own copy of that
parser (`grantPermits`) and watching your own copy fail proves your two
pieces of code are internally consistent; it proves nothing about `visudo`.
When the checker under test *is* the real consumer, breaking-your-own-guard
is the right move. When the real consumer lives outside your process, the
only thing that plays the equivalent role is calling it.

## Why This Matters

A reimplementation of a parser's rules is a hypothesis about that parser,
not a specification of it. Sudoers' escaping rules — `:` is a mandatory list
separator that must be escaped inside an argument, `=` is escapable but not
mandatory in this position — are exactly the kind of detail that's easy to
get subtly wrong and that a hand-rolled matcher will happily agree with
itself about, because the matcher was written from the same (incomplete)
mental model as the generator. The two pieces of code drift together, not
apart, so tests built entirely from that shared model can be arbitrarily
thorough — eight test cases in this one — while remaining
completely blind to the one failure that would actually matter in
production.

The instinct to write a fake or a model instead of invoking the real thing
usually comes from a reasonable place: the real tool is slow, environment
-dependent, or not installed everywhere. Those are real constraints, and the
fix here respects them (`visudoAvailable()` + `it.skip`) rather than
overriding them. But the constraint should shrink the test's footprint, not
license replacing the real consumer with a reimplementation of it. A skipped
test that runs nowhere is honestly absent evidence. A green test against
your own model is dishonestly-presented evidence — it looks like proof and
isn't.

## When to Apply

- The code under test generates an artifact — a config file, a rule, a
  script, a serialized payload — that is parsed or executed by a real
  external program you don't control (sudoers, cron, systemd units, shell
  scripts, another service's config format).
- You're about to write, or are reviewing, a test where the only assertions
  run against a function shipped in the same change as the code under test,
  and the actual consuming binary/library never appears in the test file.
- You're adding a "this check isn't vacuous" fixture for an external format.
  Don't hand-pick a string that merely looks malformed — run it through the
  real tool first and confirm it's rejected for the reason you think.
- The real tool might be absent in some environments (CI images, sandboxes).
  Gate the real-tool tests with an availability probe and `it.skip`, don't
  substitute a mock in its place.

## Examples

**Before** — scoping proven only against a self-written matcher
(`tests/cli/reach-grant.test.ts:27-46`, using `grantPermits` from
`bin/tinstar/reachGrant.js:58-67`):

```ts
it('permits exactly the two serve invocations Tinstar issues', () => {
  expect(grantPermits(RULE, '/usr/bin/tailscale serve --bg --yes --https=443 http://127.0.0.1:5273')).toBe(true)
  expect(grantPermits(RULE, '/usr/bin/tailscale serve --bg --yes --https=443 off')).toBe(true)
})
// ...six more test cases, all against grantPermits, never against visudo.
```
This suite was fully green while the rule it exercised could not parse — the
literal `http://127.0.0.1:5273` in the fixture contains the same unescaped
`:` that made every real install fail.

**After** — the real parser is invoked, gated on availability, and proven
non-vacuous with a fixture that was actually watched failing
(`tests/cli/reach-grant.test.ts:246-273`):

```ts
function visudoCheck(rule: string): { ok: boolean; output: string } {
  const dir = mkdtempSync(join(tmpdir(), 'tinstar-sudoers-'))
  const file = join(dir, 'tinstar-reach')
  writeFileSync(file, `${rule}\n`, { mode: 0o600 })
  try {
    execFileSync('visudo', ['-cf', file], { stdio: 'pipe' })
    return { ok: true, output: '' }
  } catch (err) { /* ... */ }
}

describe('the generated rule parses as real sudoers', () => {
  const realIt = visudoAvailable() ? it : it.skip

  realIt('is accepted by visudo -c', () => {
    expect(visudoCheck(RULE).ok).toBe(true)
  })

  realIt('rejects a malformed rule, so the check above is not vacuous', () => {
    // `will ALL=(root) NOPASSWD` is NOT a usable fixture: visudo parses it
    // as a Cmnd_Alias reference and exits 0. Confirmed empirically.
    expect(visudoCheck('will ALL=(root').ok).toBe(false)
  })

  realIt('rejects the unescaped form, which is what shipped before', () => {
    expect(visudoCheck(
      'will ALL=(root) NOPASSWD: /usr/bin/tailscale serve --bg --yes --https=443 http://127.0.0.1:5273',
    ).ok).toBe(false)
  })
})
```

The `grantPermits`-based tests weren't deleted — they're still useful for
asserting the *intended* scoping quickly and without shelling out — but they
now sit alongside, not in place of, tests that ask the real parser whether
the artifact is even legal. The install path itself carries the same lesson
forward defensively: `installReachGrant` in
`bin/tinstar/commands/service.js:306-317` runs `visudo -cf` on the staged
file before every real install, so even if a future test regresses, the
runtime path still refuses to write a rule the real parser rejects.
